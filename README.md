# Balancing Robot

## Introduction
This is an ongoing personal project started on 02/08/2026. Up to 17/09/2026 the budget was kept within £60. The aim is to build a self-balancing robot and learn about control. PID tuning was unsuccessful, so I moved to LQR.

## Hardware
Both the PCB and the robot frame were designed by me, with the PCB manufactured by JLCPCB and the frame 3D printed at home. The bottom layer and motor brackets take the most vibration, so carbon-fibre PETG was chosen for its rigidity. The rest of the frame is PLA, which was easier to print and has no special strength requirement.

Main parts: STM32F103C8T6 (Blue Pill), TB6612FNG motor driver, GA12-N20 500 rpm geared motors with Hall encoders, a GY-521 IMU board (it carries an ICM-20689 rather than an MPU6050, but the firmware still calls it MPU6050), an HC-05 for Bluetooth, and 4×AA cells.

## Software
Development was staged so each part was verified before the next:

| Stage | Purpose | Status |
|---|---|---|
| 0 | Confirm the clock ticks are generated correctly | Done |
| 1 | Read gyroscope and accelerometer over I2C and fuse a pitch angle | Done |
| 2 | Send IMU data to the laptop over UART via HC-05 | Done |
| 3 | Receive commands over Bluetooth and check the motors respond | Done |
| 4 | PID balancing attempt | Did not balance |
| 5 | LQR controller with gains from the MATLAB model | Balances hands-off, best runs 20-40 s; runs vary, tuning continues |

See [software/](software/) for the firmware, test logs and a note on how Claude was used.

## MATLAB simulation
After PID failed despite continued tuning, I hypothesised the 500 rpm motors didn't have enough torque. I simulated the robot in MATLAB and the results showed there is theoretically enough torque. Later system identification on the real robot agreed: the motors behave close to the model.

To reduce development time I then chose LQR, with the model tested and simulated in MATLAB. I measured the period of oscillation in a pendulum test to get the inertia, plus the height from the centre of mass to the wheel axis, the encoder CPR, the mass and the wheel radius. The MATLAB simulation files were generated by Claude, as I was new to MATLAB.

## What was really wrong
The LQR ported from the simulation failed within 1-2 s on hardware. I added logging (a RAM log dumped over Bluetooth after each run) and, with Claude's help analysing the logs, found that the angle and rate reached the controller about 20-30 ms later than the wheel encoder. The simulation had missed this because it delayed all signals together. A model of the firmware's exact signal path showed that this uneven lag makes the loop unstable. Raising the IMU sample rate to 1 kHz and widening the gyro filter took the robot from falling in 1-2 s to balancing for 20-40 s.

My earlier hypothesis that motor deadband was the root cause turned out to be only a secondary effect: the log shows the wheels don't move until the command reaches about 0.5-1 V, and I'm testing compensation for that.

## Current Result
The longest run is 40 s (ended when I tripped it), with the code in `software/known_good_firmware`. A demo clip is in [demo video](demo/first_success_clip.gif). Pitch is controlled, but position holding is not working yet: the robot surges forward and backward over 1-2 m, chatters at about 8 Hz with the motor command saturated about half the time, and falls when the wheels reach their no-load speed. This is what I'm working on now.
